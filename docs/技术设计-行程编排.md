# 行程编排引擎 · 技术设计（出口级公交路线）

> v0.1 ｜ 2026-10-26 ｜ 配套 [方案蓝图.md](方案蓝图.md)
> **已有可运行原型**：[../prototype/README.md](../prototype/README.md)（Python，成都数据，3 天 8 点 12ms 出可行解，勾选边际成本 4—5ms）
> 目标：把"用户勾选景点 → 出口级公交/地铁 + 步行 + 停留时长"的链路拆成可实现的工程模块

---

## 1. 一句话架构判断

**地图 API 是"事实"，求解器是"决策"，LLM 是"表达"。三者不能互换。**

- 单段怎么走、坐几号线、哪个出口、多少米、多少分钟 → **必须来自地图开放平台的路径规划接口**，不能让模型生成。
- 一天怎么排、先去哪后去哪、每个点待多久、时间够不够 → **约束优化**，不是排序算法随便排。
- 怎么讲给用户听、为什么这么排、有什么备选 → **LLM**，只允许转述结构化事实。

> 答辩金句："模型负责听懂人话和说人话，地图负责事实，求解器负责算得对。"

**这条边界就是你和小红书、和通用大模型的根本区别**：它们给你"地点"，你给"可执行的时刻表"。

## 2. 三层职责边界

| 层 | 输入 | 输出 | 由谁负责 | 典型失败模式 |
|---|---|---|---|---|
| **事实层** | 起点/终点坐标、出发时刻 | 步行段、公交/地铁段（线路、方向、上下车站、出口、站数、票价）、总耗时 | 地图开放平台 API + 自建出口库 | 限流、数据缺失、末班车后无方案 |
| **编排层** | 选中 POI 集合、开放时间、停留时长、两两耗时矩阵、预算/体力约束 | 每天访问顺序 + 每点到达/离开时刻 + 用餐与缓冲 | OptVerse 求解器 / 启发式 | 无可行解、求解超时 |
| **表达层** | 结构化行程 JSON | 自然语言讲解、排序理由、贴士、备选方案 | LLM（受 Schema 约束） | 幻觉、编造不存在的站 |

**强制规则**：表达层**禁止**新增任何地点、线路、时刻。生成后跑一遍校验：文本里出现的每个站名/线路，必须能在结构化 leg 里找到；找不到就丢弃重写。

## 3. 数据源矩阵

| 数据 | 来源 | 获取方式 | 更新频率 | 备注 |
|---|---|---|---|---|
| POI 名称/坐标/分类 | 地图开放平台 POI 检索 | API | 周 | 演示城市 300—500 条 |
| 开放时间/闭馆日/门票/预约要求 | 景区/博物馆官网 + 官方公众号 | **人工录入**（100—200 条） | 月 | 必须存 `source` 与 `updated_at`，答辩要用 |
| 建议游览时长 | 官方推荐 + 我们的默认值 | 规则表 | — | 分人群系数：带娃 ×1.4、带老人 ×1.3、打卡 ×0.6、深度 ×1.5 |
| 单段路径（步行/公交/地铁/驾车） | 地图开放平台路径规划 API | API | 实时 | **唯一事实源**，结果缓存 |
| 地铁出口 | 地图 POI「出入口」+ 站内图人工整理 | 半自动 | 月 | 演示只需 10—20 个站，每个站 2—8 个出口 |
| 出口设施（直梯/扶梯/无障碍） | 人工整理 | 人工 | 季 | 带老人/推车场景的加分项 |
| 首末班车、发车间隔 | 地图 API 部分返回 + 人工 | 混合 | 季 | 夜间自动切打车兜底 |
| 天气 | 和风 / 华为云市场天气 API | API | 小时 | 触发"下雨重排" |
| 排队/人流 | **无稳定公开源** | 时段热度模型估算 | — | 诚实说明是估算，别吹成实时 |
| 两两耗时矩阵 | 由单段 API 批量生成 | 预计算 | 7 天 TTL | **省钱关键**：N 个点只算 N² 次，不是每次请求都现算 |

## 4. 编排建模

### 4.1 问题定义

给定：
- 用户选中的点集 `P`（通常 4—10 个/天）
- 天数 `D`，每天可用时间窗 `[T_start, T_end]`（如 09:00—21:30）
- 点 `i`：开放窗 `[o_i, c_i]`、建议停留 `d_i`、门票 `f_i`、满意度 `s_i`
- 两两出行时间 `t_ij`（含步行 + 等车 + 车内 + 换乘 + 缓冲）、费用 `c_ij`
- 预算 `B`、体力上限 `W`（总步行米数/爬坡量）

求：点分配到各天 + 每天访问顺序 + 每个点的到达/离开时刻，使总交通时间最小、满意度最大，且全部约束可行。

### 4.2 约束清单（按重要性）

```
C1 每个选中点恰好访问一次（或允许跳过，带惩罚）
C2 到达 i 时刻 >= o_i；离开 i 时刻 <= c_i - 停止入场提前量(30min)
C3 arrive_j = leave_i + t_ij            （时间推进，t_ij 已含缓冲）
C4 每日结束 <= T_end
C5 午餐窗 11:30—13:30 内安排 45—60 分钟用餐（可放宽到 14:00）
C6 总步行 <= W；单段步行 > 1.2km 时优先给公交方案
C7 预算：Σ门票 + Σ交通 <= B
C8 换乘冗余：跨线换乘额外 +3 分钟/次；同站换乘 +2 分钟
C9 首末班车：末班后无地铁 → 自动改打车方案并提示费用变化
C10 闭馆日 / 周一闭馆 等规律性约束
```

### 4.3 目标函数

```
min  Σ_leg t_ij  +  λ1·Σ等待时间  +  λ2·Σ跳过惩罚  −  λ3·Σ满意度
s.t. C1—C10
```

线性加权的好处：**可解释、可调参、可现场演示**（"把'不想太累'拉满，你看它自动把点减到 4 个"）。λ 权重就是产品里的"节奏滑杆"。

### 4.4 求解策略（务实分阶段）

1. **小规模**（≤10 点/天）：直接交 OptVerse 天筹求解器做带时间窗的 TSP/VRP，求近优解。
2. **中等规模**：先按地理聚类 + 开放时间把点分到各天（减少组合爆炸），每天独立求解。
3. **超时兜底**（>5 秒）：贪心插入 + 2-opt / or-opt 局部搜索，保证有解返回。
4. **无解处理**：按顺序松弛——延长单点停留上限 → 跳过最低满意度点 → 放宽午餐窗 → 提示"加一天"。**每次松弛都要告诉用户牺牲了什么**，这比悄悄给个烂方案强得多。

> 评委问"为什么不用纯 LLM 排"，就展示这一步：让 LLM 排"宽窄巷子 10:00、武侯祠 10:15"，指出两地相距 6 公里，不可行。

### 4.5 增量重算（体验的核心）

| 触发 | 策略 | 目标耗时 |
|---|---|---|
| 勾选/取消一个点 | 固定其它点顺序，做插入/删除 + 局部 2-opt | < 300ms |
| 改节奏/预算滑杆 | 只重算权重与筛选，不重算路径矩阵 | < 500ms |
| 天气/闭馆/晚点 | **锁定已完成的段**，只重排剩余天/剩余点 | < 1s |
| 换端继续编辑 | 版本号 + 乐观锁，冲突时给"合并/覆盖"选择 | — |

返回结构里必须带 **diff**：`+38 分钟交通 / +1.2km 步行 / +12 元`，前端的"选点即算代价"就靠它。

## 6. 时间估算模型

```
t_leg = walk_to_stop + wait + in_vehicle + transfer_walk + walk_to_dest + buffer
```

| 参数 | 取值 | 说明 |
|---|---|---|
| 步行速度 | 成人 1.2 m/s，老人 1.0，带娃 0.9 | 按同行人自动调整 |
| 等车时间 | 地铁 发车间隔/2（3—5 min）；公交 发车间隔/2（5—10 min） | 有实时到站数据优先用实时 |
| 换乘步行 | 同站 2—4 min，跨线 4—6 min，大站 +3 min | 用站内图校正 |
| 景区内步行 | 小型 10 min，大型（如宽窄巷子/古镇）20—30 min | 单独加，别漏 |
| 缓冲 | 每段 +5 min，当天首段 +10 min（找路） | 宁可早到 |

**误差目标**：抽样 20 条实际走一遍，预测 vs 实际 ≤ 15%。这个数字写进 PPT，比任何形容词都有说服力。

## 7. 验收标准（P0 必须全部满足）

- [ ] 单城市 8—12 个 POI、3 天行程，端到端生成 < 8 秒
- [ ] 勾选/取消一个点，边际成本返回 < 1 秒
- [ ] **100% 时间窗可行**：自动化脚本校验每个 `arrive/leave` 与开放时间、时间推进关系
- [ ] 地铁段出口级描述覆盖率 ≥ 90%
- [ ] 每段 leg 都能追到地图 API 原始返回（留日志，答辩可查）
- [ ] 天气触发重排后，已确定的前一天行程不变（局部修复生效）
- [ ] 20 条人工走查，时刻误差 ≤ 15%

## 8. "为什么不用华为自己的地图"——提前准备答案

评委大概率会问。标准答法：

> "单段公交导航需要全国路网与实时公交数据，C 端地图开放平台更成熟，我们采购它作为**事实层**，保证准确与合规。**华为云承担的是编排、AI、存储、调度**——这正好是赛题一要的'基于华为云产品打造 AI 应用'。我们的创新不在再做一个导航，而在**把导航能力编排成一份可执行的行程**；导航可以买，编排策略必须自研。"

补充（如果问到国产化）：可展示 KooMap 用于景区影像/三维底图的可选方案，以及 POI 数据来源合规说明。

## 9. 本周就能验证的三个技术假设

这三件事任何一件不成立，方案都要改，**所以先做，别先写 UI**：

1. **公交 API 能否稳定返回"站名 + 线路 + 方向 + 步行段"**：写个脚本，对 20 组起终点跑一遍，统计字段完整率与耗时。
2. **地铁出口数据是否可得**：用 POI「出入口」检索 + 站内图核对，先做 5 个站。
3. **求解器求解时间**：10 个点、带时间窗，OptVerse 试用账号跑一次，记录耗时；若 >5 秒就准备启发式兜底。

> 三个都过了，再动手写端；任何一个不过，先改方案再写代码。这一步能省你两周。
